# Longway Agent Notes

## Product direction

- Longway is a Swift compiler for a Scheme-inspired language that emits Apple Shortcut property lists.
- Keep the source language in a normal programming model. Apple Shortcuts actions, UUIDs, and magic-variable wiring are compiler implementation details rather than source-level workflow syntax.
- Ship and verify a focused MVP before expanding the action catalog or language surface.

## Language semantics

- A program contains one or more `(define (name parameters …) body … result)` forms. Each definition compiles to a standalone Shortcut named after the function; legacy `(shortcut …)` forms are invalid.
- Parameters and return values have no source-level type annotations. Infer number, text, and Boolean constraints across function bodies and recursive call graphs; leave genuinely unconstrained values generic and reject only provable conflicts.
- The final form produces the function result. Earlier forms may perform actions for side effects; a final `show-result` both shows and returns its argument.
- Direct and mutual recursion are valid. Calls are name-linked to independently installed Shortcut artifacts. A definition whose entire body is one direct self-call in tail position (through `let` and `if`, with no `notification`/`open-url`/`wait`/`show-result` on that path) is tail-call optimized into a bounded in-workflow loop instead; everything else — mutual recursion, non-tail self-calls, multi-form bodies — keeps calling the generated Shortcut recursively and is not tail-call optimized.
- Embed direct literals in consuming action parameters when the parameter schema permits it; do not materialize them merely to make them referenceable.
- A `let` binding materializes a value as a UUID-bearing Shortcut action so other expressions can reference it. Bound literals emit Text or Number actions; references serialize the producer action's output UUID.
- Do not rely on implicit previous-action output. Every generated dependency must be wired explicitly.
- `let` is lexically scoped and follows Scheme `let` initializer semantics: initializers see the outer environment, not sibling bindings. Shadowing in nested scopes is allowed; duplicate names in one binding list are errors.
- `(text ...)` is not a public statement and `(show-result)` without an argument is invalid.
- Numeric `=`, `<`, `<=`, `>`, and `>=` accept at least two operands and compare each adjacent pair, matching Scheme-style chained comparison semantics.
- `string-append` accepts text operands and `number->text` performs the explicit numeric conversion needed for interpolation. Mixed literal/action-output token ranges are UTF-16 offsets, matching WorkflowKit's NSRange serialization.
- `split-lines`, `split-whitespace`, and `split-text` return lists. `split-text`'s custom separator, interactive prompts, and `format-current-date`'s Unicode date format are literals in the focused MVP because those are the parameter shapes confirmed from copied Shortcuts actions.
- `choose-from-list` returns a generic value, `ask-text` returns text, and `ask-number` returns a number. These interactive forms are side effects and disqualify tail-call loop optimization even when nested in a `let` initializer or another value expression.
- A list crosses a function call in both directions: an argument as an array-typed dictionary field, a result as the ordinary single-attachment Stop and Output token the Shortcuts editor itself writes for a list variable. Do not pass a list through a *text*-typed dictionary field; that flattens it to newline-joined text, which reads back as one item, so `Count` then reports the line count while `Get Item from List` sees a single item and any index past the first fails at runtime. A tail-call-optimized self-call never leaves the shortcut and bypasses the question.
- `(list ...)` builds a flat Shortcuts list of untyped elements; `length`, `list-ref`, `first`, `last`, and `empty?` read from one. `list-ref` indexes from 0 like Scheme. Elements carry no static type, so a read returns a generic value that its consumer re-types; a list element may not itself be a list or a dictionary, because a nested collection would be serialized into its parent as text. Constrain list operands to the list type and reject provable non-lists; there is no literal list value, so a list operand always resolves to an action output.
- `(dict k v …)` builds a Shortcuts dictionary from alternating keys and values; `dict-ref`, `dict-keys`, `dict-values`, and `dict-set` work on one. Keys are text and values are untyped, so a `dict-ref` returns a generic value exactly as a list read does, and `dict-keys`/`dict-values` return lists. Reject a duplicate literal key. Unlike a list, a dictionary field *can* hold a list or another dictionary, because the dictionary-field encoding has a distinct item type for each; only `dict-set` cannot, since its value rides in a text-shaped parameter. `dict-set` answers a new dictionary rather than mutating its argument, and like a list a dictionary has no literal value, so an operand always resolves to an action output.
- Shortcuts reads `.` in a dictionary key as a key path into nested content — Apple's own help text gives `beverages.1.favorite` — so `(dict-ref d "a.b")` does not address a literal key named `a.b`. This is not rejected; it is a documented sharp edge.
- `dict-has-key?` is deliberately absent. Shortcuts has no key-membership action, and the obvious lowering — comparing `(length (dict-keys d))` before and after a `dict-set` — silently corrupts the dictionary if Set Dictionary Value turns out to mutate in place rather than copy. Adding it needs either that mutation question settled on a device or text conditions, which this compiler does not yet lower.
- `if` requires a Boolean condition, consequent, and alternative. It can select values with compatible inferred types or select action forms; only the selected branch executes.
- Preserve source locations in semantic diagnostics.

## Shortcut lowering invariants

- Use `is.workflow.actions.gettext` for Text actions.
- Serialize literal text as `WFTextTokenString` with an empty `attachmentsByRange` dictionary.
- Serialize an action-output text reference as a `WFTextTokenString` containing one object-replacement character and an attachment with `Type`, `OutputName`, and `OutputUUID`.
- Lower `+`, `-`, `*`, and `/` expressions with at least two operands to explicit `is.workflow.actions.math` actions. Materialize a literal left operand with `is.workflow.actions.number`, chain variadic operations left-to-right, and identify each result as `Calculation Result`.
- Lower numeric `<`, `<=`, `>`, `>=`, and `=` with Shortcut condition codes 0, 1, 2, 3, and 4. Code 4 renders as Shortcut’s `is` condition and performs equality on a typed Number input. Chain variadic comparisons through nested short-circuit conditional blocks.
- No numeric condition on a Number input has a variable slot — the editor only accepts a typed number, for `is` and for every relational condition — so "this number is greater than that number" has no serialization at all. Lower a comparison against a non-literal operand as a Math subtraction tested against a literal zero: `a < b` becomes `a - b < 0`, and the ordering of the difference against zero matches the ordering of the operands for every condition code. A comparison against a literal keeps that literal in `WFNumberValue`.
- Shortcut Input dictionary extraction and Run Shortcut results are runtime-generic even when Longway inferred a concrete type. Pass them through Number or Text before using them as typed conditional inputs.
- A numeric condition's comparison value always goes in `WFNumberValue` as a literal. Never write it to `WFConditionalActionString`: that field belongs to text conditions, and on a Number input it imports cleanly and is then never read, so the condition silently never matches — at runtime that looks like a loop overrunning its bound, not like a failed comparison.
- Represent Boolean values as typed Text producers containing `#t` or `#f`. Lower `not`, short-circuit `and`, short-circuit `or`, and source `if` to `is.workflow.actions.conditional` blocks sharing a `GroupingIdentifier`; typed value conditionals reference the End If UUID as `If Result`.
- Ensure each value-producing `if` branch ends with an action of the branch type. Pass referenced Text/Boolean values through Text and referenced Number values through Number so Shortcuts gives `If Result` the intended runtime value.
- Conditional `WFInput` must wrap the `WFTextTokenAttachment` as `{ Type: "Variable", Variable: attachment }`. A bare attachment passes plist validation but imports with an unset If condition.
- Functions with parameters enable `WFWorkflowHasShortcutInputVariables`, accept `WFDictionaryContentItem`, and read each named argument with `is.workflow.actions.getvalueforkey` from a `Type: ExtensionInput` attachment.
- Serialize a list argument as a `WFItemType` 2 dictionary field whose `WFValue` is a `WFArraySubstitutableParameterState` wrapping the variable's `WFTextTokenAttachment` — not as a text field, which flattens it. `WFItemType` 3 for a number field is confirmed by the same source.
- `WFItemType` is WorkflowKit's own `WFPropertyListParameterValue` numbering: 0 text, 1 dictionary, 2 array, 3 number, 4 boolean, 5 file. It is *not* the numbering third-party documentation gives (which has 1 number and 3 dictionary), and the two disagree on exactly the values a dictionary field needs. Each item type substitutes a whole-field variable through its own parameter state class, and the serialized `WFSerializationType` is that class's name: `WFArraySubstitutableParameterState` for an array and `WFDictionarySubstitutableParameterState` for a dictionary. Longway keeps Booleans at item type 0 because it represents them as `#t`/`#f` text rather than as Shortcuts Booleans.
- Lower a function call to `is.workflow.actions.dictionary` followed by `is.workflow.actions.runworkflow` with explicit `WFInput`, `WFWorkflowName`, UUID, and output name. Recursive calls use the same mechanism, except tail-recursive self-calls (see below).
- Lower a tail-call-optimized definition to `is.workflow.actions.setvariable`/`is.workflow.actions.getvariable` on one named Shortcuts variable per parameter (referenced as `{ Type: "Variable", VariableName: <parameter name> }`, distinct from the `{ Type: "ActionOutput", OutputName, OutputUUID }` shape used everywhere else) plus a hidden `#result` variable — `#` cannot start a source identifier, so it can never collide with a real parameter. Wrap the per-iteration body in `is.workflow.actions.repeat.count` (`GroupingIdentifier` + `WFControlFlowMode` 0/2, `WFRepeatCount` = `tailCallLoopLimit`) rather than a recursive `runworkflow` call. Always force a concrete runtime type (`emitValue`, not the passthrough `materialize`) before writing to a loop variable. Named-variable Get Variable reads are still runtime-generic to the Shortcuts editor even though a concrete type was written (`isRuntimeTyped: false`, exactly like dictionary extraction and Run Shortcut results): skipping that and trusting the read directly compiles fine but silently produces a conditional whose input type Shortcuts can't infer, which the editor renders as a vague "is anything" condition instead of "is 0". A base case ends with an inline `is.workflow.actions.output` — Shortcuts' "Stop and Output" is that same action, which both returns the value and halts the workflow ("no more actions will be run after this action"), and is explicitly supported inside `If` branches as a multi-exit `return`. Do not use `is.workflow.actions.exit` ("Stop This Shortcut") here: it halts without producing any output, so the function would return nothing on its fast path. The loop therefore only runs as many iterations as the recursion needs; `WFRepeatCount` = `tailCallLoopLimit` is a safety cap for recursion that never reaches a base case, not the expected iteration count. A base case still writes `#result` before that inline output purely as a fail-safe: if the inline output did not halt, the loop would keep re-deciding the same base case and the post-loop read would return the same value. Side-effecting actions on the path to the self-call still disqualify optimization even though a correctly-halting base-case output would make the base-case side of that safe: value correctness degrades gracefully if the inline output somehow doesn't halt from inside the nested Repeat/Conditional blocks (the loop just falls through to the existing bound-and-read-`#result` path, unchanged), but a side effect firing on every remaining idle iteration instead of once would not degrade gracefully — and that halting behavior from this nesting depth has not been confirmed on a real device.
- Lower `(list ...)` to `is.workflow.actions.list`. `WFItems` is a `WFContentArrayParameter`, not the keyed field list a Dictionary action takes: write a plain string per literal item and a text token string for an item that references another action's output. Wrapping items in `WFItemType`/`WFValue` pairs makes Shortcuts read the entire array as one item, which surfaces at runtime as "the list has only 1". The List action flattens a variable's contents into the surrounding list, which is the mechanism a future `append`/`cons` should use. Lower `length` to `is.workflow.actions.count` with `WFCountType` `Items` — that action names its input `Input`, not the `WFInput` everything else here uses. Lower `first`/`last`/`list-ref` to `is.workflow.actions.getitemfromlist` with `WFInput` and `WFItemSpecifier` `First Item`/`Last Item`/`Item At Index` (the serialized value capitalizes `At`; only the editor's display string is "Item at Index"). Shortcuts indexes lists from 1: offset a literal `list-ref` index at compile time and a computed one with a Math action, since `WFItemIndex` holds one value rather than an expression. `empty?` has no Shortcuts action — lower it as `Count` compared to literal zero through the existing equality path. Get Item from List output is runtime-generic (`isRuntimeTyped: false`), like dictionary extraction.
- Lower text splitting to `is.workflow.actions.text.split`, whose input key is lowercase `text`. Omit `WFTextSeparator` for lines, use `Spaces` for whitespace, and use `Custom` plus a bare `WFTextCustomSeparator` string for a custom separator. Lower selection to `is.workflow.actions.choosefromlist` with `WFInput` and `WFChooseFromListActionPrompt`; its result is runtime-generic. Lower prompts to `is.workflow.actions.ask` with `WFAskActionPrompt`, adding `WFInputType: Number` only for `ask-number`. Lower `format-current-date` to `is.workflow.actions.format.date` with `WFDateFormatStyle: Custom`, a bare `WFDateFormat`, and a `WFDate` text token whose sole attachment is `{ Type: CurrentDate }`. These shapes come from the 28-action Shortcut copied through `com.apple.shortcuts.action`, where each selected action was a separate pasteboard item.
- Lower `(dict ...)` to `is.workflow.actions.dictionary`, the same action and `WFItems`/`WFDictionaryFieldValue` shape the function-call ABI already builds its argument dictionary with. Lower `dict-ref`, `dict-keys`, and `dict-values` to `is.workflow.actions.getvalueforkey` under `WFGetDictionaryValueType` `Value`, `All Keys`, and `All Values`; that action takes `WFInput` and names its output `Dictionary Value`. Lower `dict-set` to `is.workflow.actions.setvalueforkey`, which takes `WFDictionaryKey`, `WFDictionaryValue`, and — the trap — `WFDictionary` rather than the `WFInput` its Get counterpart uses, in the same family of mistake as Count's `Input`. Write `WFDictionaryKey` as a bare string for a literal key, which is what Apple's Gallery shortcuts do, and as a token string for a computed one. Get Dictionary Value output is runtime-generic (`isRuntimeTyped: false`), like every other dictionary extraction.
- Never pass a list or a dictionary through Text or Number: Text flattens a list to newline-joined text and a dictionary to JSON. Republish either under a new UUID with `is.workflow.actions.getvariable` (`emitPassthrough`), which is what `emitValue` does for the list, dictionary, and generic types, so tail-call loop variables and conditional branches keep the runtime value intact. A function returning a list emits the generic output content classes, since Shortcuts has no list content class; a function returning a dictionary emits `WFDictionaryContentItem`, which does exist and is the class the function-call ABI already declares on the input side.
- End every function with `is.workflow.actions.output`. Set workflow output content classes from the inferred return type, or emit the supported generic classes when inference leaves it unconstrained.
- Keep function shortcuts out of the Share Sheet by emitting empty `WFWorkflowTypes`.
- Signing remains opt-in through Apple's `shortcuts sign` command. Sign every artifact before writing destinations, and replace each destination atomically so a failed signer does not destroy existing files.
- Generated `.shortcut` artifacts are ignored and should be rebuilt rather than committed.

## Verification

Run these before claiming a compiler change is complete:

```sh
swift test
swift build -c release
.build/release/longway check Examples/hello.longway
.build/release/longway check Examples/morning.longway
.build/release/longway check Examples/math.longway
.build/release/longway check Examples/logic.longway
.build/release/longway check Examples/comparison.longway
.build/release/longway check Examples/conditional.longway
.build/release/longway check Examples/functions.longway
.build/release/longway check Examples/identity.longway
.build/release/longway check Examples/lists.longway
.build/release/longway check Examples/dicts.longway
.build/release/longway check Examples/transaction.longway
```

For serialization changes, inspect the emitted unsigned plist and verify UUID references point to the intended producer action. When signing behavior changes, exercise the real Apple signer against an existing destination.

For function ABI, recursion, runtime typing, or conditional serialization changes, signing and import preview are not sufficient verification. Replace the installed artifacts, confirm their names have no automatic numeric suffix, and run a finite caller through `/usr/bin/shortcuts run`; verify both its returned value and termination. A visible magic-variable label does not prove that Shortcuts resolved its runtime value.

The tail-call loop lowering specifically has not yet been run through the real Shortcuts app (signing plus `shortcuts run` needs an interactive Apple ID) — it is only verified against the unsigned plist structure via `swift test`. Before relying on it, sign and run `Examples/functions.longway`'s `sum-to` (e.g. `sum-to 10 0` should return `55`) through `/usr/bin/shortcuts run`, and separately confirm a case near/above `tailCallLoopLimit` behaves as documented (returns the accumulator's state at the bound, not a crash) rather than assuming the plist shapes for `is.workflow.actions.setvariable`/`getvariable`/`repeat.count` researched from third-party Shortcuts-format documentation are exactly right. In particular, confirm the base case's inline `is.workflow.actions.output` genuinely halts from inside the nested `repeat.count`/`conditional` GroupingIdentifier blocks it fires in — e.g. that `sum-to 3 0` returns `6` promptly rather than visibly iterating toward 2000 — and that it returns the value rather than stopping empty-handed.

WorkflowKit can also be *run*, which beats reading strings whenever the answer is a number or a nested shape rather than a spelling. `dlopen` the framework from an ordinary process — no entitlements needed for this — and drive its serialization classes directly:

- `WFPropertyListParameterValue` is the dictionary-field value model. `-initWithString:`, `-initWithNumber:`, `-initWithBoolean:`, `-initWithArray:`, and `-initWithDictionary:` each answer an object whose `-valueType` is the `WFItemType` integer and whose `-serializedRepresentation` is the exact `{ WFItemType, WFValue }` plist Shortcuts writes. That is where the item-type table above comes from. `+classForValueType:` and `+localizedTitleForValueType:` enumerate the rest.
- `-initWithSerializedRepresentation:variableProvider:parameter:` parses a field *you* emitted, so a candidate shape can be round-tripped through Apple's own reader and its `-containedVariables` checked to confirm the variable reference actually resolved. Round-trip a known-good shape from the pasteboard alongside the candidate as a control; the dictionary-field encoding was confirmed this way against the array field the editor had already produced. Note that this class models only the value half of a field — `WFKey` lives in the enclosing pair and is absent from the round-trip — and that it drops an empty `attachmentsByRange`, so compare `WFItemType` and `WFValue` rather than the whole item.

`WFActionRegistry` is *not* usable this way: outside the Shortcuts app its providers do not load and `-createActionWithIdentifier:serializedParameters:` answers a `WFMissingAction`, so action output names and parameter classes still have to come from strings or from the editor.

Apple's own shortcuts and WorkflowKit itself are on disk and settle action-format questions that third-party documentation guesses at. `/System/Library/PrivateFrameworks/WorkflowKit.framework/Resources/Gallery.bundle/Contents/Resources/*.wflow` are Apple-authored workflow property lists; `strings` over the WorkflowKit images in `/System/Volumes/Preboot/Cryptexes/OS/System/Library/dyld/dyld_shared_cache_arm64e.*` yields every action identifier, parameter key, and string-enum value, spelled `Display Name (ParameterKey)`. Check both before inventing a plist shape: the list lowering's `WFItems`, `Input`, `WFCountType`, `WFItemSpecifier`, and `WFItemIndex` spellings all come from there, and the first two were wrong when they were guessed from third-party documentation.

What list support still lacks is device evidence for the in-function path: `swift test` checks plist structure, and `Examples/lists.longway` has not been signed and run. `report` should show `Ada`, and `sum-list` should total a list handed to it as `{ items: [3, 4, 5], index: 0, total: 0 }` from the Shortcuts app. Two earlier list bugs were both caught by running, not by reading plists: a `WFItemType`/`WFValue` wrapper around `WFItems` entries collapsed a list into one item, and the Count action's input was written as `WFInput` instead of `Input`.

The array-field encoding above came from a shortcut built by hand in the Shortcuts editor and copied to the pasteboard, which is the cheapest way to get a real plist when one is needed: the editor writes each selected action to the pasteboard under the `com.apple.shortcuts.action` type as a binary property list, readable with AppKit (`NSPasteboard.general`) and no special permissions. The Shortcuts database under `~/Library/Shortcuts/` is TCC-protected and unreadable without Full Disk Access, and an exported `.shortcut` is an AEA archive that `aea decrypt` will not open without the signing key, so the pasteboard is the practical route. Ask the user to build the smallest shortcut that shows the shape in question and copy it.

A list-returning function still emits the generic output content classes, since Shortcuts has no list content class; whether that metadata affects how the Run Shortcut result arrives is the one part of the list ABI with no artifact behind it.

Dictionary support is verified to the same depth and no further: `swift test` checks plist structure, every emitted dictionary field round-trips through WorkflowKit's own parser with its variable references resolved, and `Examples/dicts.longway` has not been signed and run. `greeting` should show `Ada`, `renamed` should answer `Grace`, `field-count` should answer `2`, and `report` should show `Ada` through a dictionary handed across a Run Shortcut call. Three specific things want device evidence, in descending order of risk:

- Whether Set Dictionary Value copies or mutates. `dict-set` is compiled as if it answers a new dictionary and leaves its argument alone; if it mutates in place, `(dict-set d …)` silently changes `d` too. This is also what blocks `dict-has-key?`.
- `WFDictionaryValue`'s parameter shape. It is written as a `WFTextTokenString`, inferred from it being a plain "Value" field with no type enumeration beside it in the action catalog, unlike `WFGetDictionaryValueType`. The round-trip check above does not cover it, because it is an action parameter rather than a dictionary field.
- `WFDictionaryContentItem` as a *output* content class. It is confirmed as an input class and as Get Dictionary Value's accepted input, but no artifact shows it in `WFWorkflowOutputContentItemClasses`.

Text splitting, list selection, typed prompts, current-date formatting, and mixed-variable Text token shapes were copied directly from a working editor-built Shortcut and are structurally covered by `swift test`. The generated `Examples/transaction.longway` artifact has not yet been signed and run; runtime verification should confirm both chooser prompts return the selected text, the amount remains numeric until `number->text`, and the final Beancount entry renders every attachment in the expected position.

## Known platform issue

The Shortcuts file-open import preview can crash in AppKit with a repeated window-layout exception, while drag-and-drop imports the same signed artifact. This has not been causally tied to one plist field and must not be reported as fixed without repeatable runtime evidence. Use drag-and-drop as the current manual import workaround.
